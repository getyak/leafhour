# Reading calendar and notebook workspace

The user approved all eight research goals and requested daily, per-book and overall reading time, implementation, PR/normal merge and production acceptance. The approved in-conversation sketch is an information architecture reference, not a shipped implementation. This approval permits a NEW explicit, selected-note analysis capability; existing reading chat/companion and external MCP permissions remain unchanged.

## Product contract

1. Independent calendar and notebook views at `/library?workspace=calendar` and `/library?workspace=notes`; preserve locale, date, book/type/topic/query selection, selection and drafts through refresh/back. Retain legacy calendar/notebook links. Sidebar entries open the workspaces. In-reader quick inspection may retain its existing overlay.
2. Calendar: compact month index and selected-day story containing real books, source anchors, questions and notes. Show recorded daily duration, monthly duration, all-time duration, and a per-book list with month/all-time duration. Include archived books. Use the existing reading-source allowlist, valid segments, timezone and interval union rules. Never count Agent chapter reads. Global totals union overlaps across books/sources; per-book totals union that book's intervals and may legitimately sum higher. No understanding score.
3. Notebook: list/detail layout, editable user comments/questions through existing optimistic edit service, original/translation quotation provenance, source return, owner-scoped local draft recovery and undo via a real revisioned edit. Highlights' source text is not editable as user prose.
4. Question development: user-controlled open/understood state, dated follow-up understandings stored separately from the original; preserve older words. State reversible. Manual topics and assignment are reusable views of the same records.
5. Semantic retrieval: retain deterministic text search; an explicitly invoked bounded selected-note search uses the configured official DSH generator, returning only allowed note keys and reasons, never invented hits. Show actual scope, not a claim of entire-library search over a truncated pool.
6. Comparison: selected-note bounded generation returns candidate supports/extends/contrasts/related relationships, each citing >=2 actual selected note keys. The reader may adopt or reject. Never turn a same-word match into an accepted relationship automatically.
7. Weekly/monthly review: user chooses notes/date scope, explicitly requests at most three evidence-linked items with a next reading/writing/question action. Output remains an attributed candidate until adopted. No automatic generation on open and no notifications.
8. Scope/ownership/recovery: authenticated current owner, explicit consent and selected saved note keys/revisions; server resolves records itself and sends <=24 notes and <=24 KiB context, with no tools/network and one bounded model request. Validate output citations against input and recheck source snapshots, owner and cancellation before publication/adoption. Preserve old notes/candidates on failure. Idempotent requests; no user balance debit without a new explicit price decision. Use capped sponsored generation (bounded daily attempts and existing provider metering) for this release. Structured workspace export/import preserves user state, topics, followups, adopted candidates and attribution; no subscription dependency. Restore validates all references before writes.

## Shared HTTP interfaces

- `GET /api/library/reading-summary?month=YYYY-MM&timeZone=...` -> `{month,timeZone,days:[existing calendar day shape],durationSeconds,readingDays,notes,questions,sourceDurationSeconds,allTime:{durationSeconds,readingDays,sourceDurationSeconds},books:[{bookId,title,author,durationSeconds,monthSeconds,sourceDurationSeconds}]}`. durationSeconds top-level is the selected month; allTime is overall recorded time.
- `GET /api/library/notebook-workspace` -> `{revision,topics:[{id,name}],recordStates:{[noteKey]:{status:'open'|'understood',topicIds:[],understandings:[{id,text,createdAt,origin:'user'}]}},relations:[],candidates:[],capabilities:{generation:boolean,maxNotes:24,maxContextBytes:24576}}`.
- `POST /api/library/notebook-workspace` -> updated same view; body `{action,id,baseRevision,...}`. Actions: `create-topic` (`name`), `assign-topic` (`noteKey,topicId,enabled`), `set-question-state` (`noteKey,status`), `add-understanding` (`noteKey,text`), `adopt-candidate` (`candidateId`), `dismiss-candidate` (`candidateId`), `remove-relation` (`relationId`). Note key is the existing JSON string `[bookId,kind,recordId]` with kind comment/question/highlight. Validate field sets, references, sizes and owner. CAS conflicts return409.
- `POST /api/library/notebook-workspace/analyze` body `{id,kind:'search'|'compare'|'review',noteKeys:[],query,consent:true,locale,workspaceRevision,sourceRevisions:{[noteKey]:integer}}`; result is a candidate `{id,kind,status:'candidate',origin:'assistant',createdAt,scope:{noteKeys,sourceHashes,sourceSnapshots},items:[{text,noteKeys,type?,next?}]}`. `type` on comparison is supports/extends/contrasts/related; next on review is reread/write/question. Search items cite at least one allowed key; compare at least two distinct keys; review <=3 items. Authenticated generator unavailable503, invalid consent/scope400/403, stale snapshot409, capped quota429. No raw exception/body in logs.
- `GET /api/library/notebook-workspace/export` and `POST .../import` support independent structured portable workspace state; body `{backup,baseRevision}`. Restore/import validates references and state before mutation, preserves ownership, and must work on another temporary instance once its base books/notes have been restored through the existing library backup.

## Ownership of implementation

Backend task owns new workspace service, time summary aggregation, limited additions to library-service for owner-bound metadata/records access, generator adapter and domain tests. It does not edit portal.mjs; return integration exports `createReadingWorkspaceService({library,dataDir,dataStore,generator,env})` with `view(user)`, `change(user,input)`, `analyze(user,input,{signal,authorize})`, `exportState(user)`, `importState(user,input)` and library `readingSummary(user,query)`.

Root owns portal HTTP wiring, response budgets, release allowlist, public assets, app views, catalogs and browser verification. `createPortal` and `createReaderServer` accept optional `notebookGenerator` for isolated tests. Existing module identity and fixed portal/reader asset budgets must remain intact; workspace loads lazily.

## Validation

Time: overlapping books/sources, duplicate events, cross-midnight and time zones, malformed segments, archived books, empty history, per-book/month/overall semantics. Notes: owner transitions/late replies, optimistic conflict, draft isolation/restore, undo, source preservation, state reversal, topic filters, export/import onto fresh instance, invalid restore no writes. Generation: consent and scope rejection, max count/bytes, malicious instructions as data, foreign/missing citations, no tools, snapshot changes, cancellation/late publication, daily cap, idempotency, explicit adoption and attributed export. UI: real source content or clearly synthetic fixtures; four locales; 320/390/768/1440; paper/night; keyboard; source-return/back and refresh.
