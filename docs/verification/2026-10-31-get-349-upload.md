# GET-349 web upload and conversation verification

Scope: web only, as confirmed by the user on 2026-10-31. Native import interaction and TestFlight are outside this change.

## Observed problems and implementation

The supplied private EPUB has 2,131 spine entries; the previous parser rejected more than 1,200. EPUB/text completion also parsed and published synchronously, returning the full book, while upload failures lost their specific reason. Upload status was confined to the floating conversation.

Optional deferred uploads now return a small durable task receipt through the existing account-bound ingestion queue. Legacy synchronous clients retain their API. A shelf task appears immediately, receives source metadata and a real cover when available, reports chapter extraction progress, and preserves failure/retry/cancellation state across server-acknowledged refreshes. No model, translation or external OCR call is added for EPUB/text. The canonical shelf entry is published after chapter storage is readable.

The library reuses the resizable conversation workspace. Desktop chat reserves page width, narrow viewports contain focus, and keyboard-sized layouts keep the composer visible while messages scroll. Upload history is a collapsed menu section. Reading preferences remain in the existing settings surface rather than interrupting conversation with onboarding or duplicating setting IDs.

Sort choices are recent reading/addition, recent addition, publication oldest/newest, and manual. Sorting composes with filters and survives URL navigation/refresh. Public catalog build timestamps are excluded from personal addition history; missing publication dates stay unknown. Automatic sorts reject cover dragging and touch long-press reordering. No reading activity is fabricated.

## Production follow-up: storage connections and bounded file transfer

Release `7ee2070375d8ceb133526cd7a939c67993f65c5f` passed CI and the existing Production smoke workflow, but authenticated real-source upload exposed a missing connection permission: its document CSP contained only `connect-src 'self'`, blocking the signed private-storage PUT before any bytes arrived. [MDN documents that this directive governs fetch connections](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src). Isolating that restriction also exposed connection closure during the large direct transfer; neither diagnostic run is counted as successful production acceptance.

The follow-up permits only the exact HTTPS storage origin from trusted deployment configuration on upload-capable surfaces, keeps script/style restrictions, rejects credentials, wildcards and non-origin configuration, and passes the actual injected environment through both hosted and self-hosted handlers.

EPUB/text clients advertising `documentChunks` now reuse the existing account-bound 2 MiB upload protocol. Its legacy PDF route names remain compatible. The server derives document mode from the file type, retains the 20 MiB document/256 MiB PDF limits, and never substitutes OCR for document parsing. Verified source-part references are adopted rather than uploading an extra complete original. A failed direct transfer switches remaining parts to bounded same-origin requests; owner and cancellation fences still run before writes.

A fresh real-browser local run enforced the actual CSP, deliberately closed the synthetic storage origin, and imported the same private EPUB through ten same-origin requests. Only the initial two signed transfers were attempted. The largest request body was 2,796,227 bytes, below the hosted request ceiling. Publication completed in about 10.8 seconds in this local fixture, original bytes remained identical, and first-chapter opening passed. This is controlled local evidence, not a production latency benchmark.

A separate reviewer approved the patch without actionable P1/P2 findings and verified a synthetic hosted CAS/Storage path with 2,320,000 source bytes: two adopted source parts, byte-identical original retrieval, other-account 404, and no OCR submission. The affected regression suite passed 140 checks; the final capability/HTTP/transport subset passed separately. Runtime, hosted build, public-package and pinned copy checks passed. Normal production upload still requires acceptance after this follow-up is deployed.
