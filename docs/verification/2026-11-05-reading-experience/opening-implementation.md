# R3 / R4 本地打开与窗口复用

日期：2026-11-05。范围按[总规格](../../superpowers/specs/2026-11-05-reading-experience-design.md)和[打开设计](opening-design.md)执行。本轮采用现有离线包与 24,000 UTF-16 正文窗口，未建立新的整书分段存储。全部新增验收使用临时目录、合成正文和隔离网络，没有读写真实账号书籍或调用模型。

## 已实现行为

首次云端下载在 `importCloud` 完成原子发布后，立即把本地书放进书架，再调用现有 `open()`。原来的前置 `/records` 同步移到阅读 session 已有的延后维护路径。首次网络下载仍需收齐整本副本。本轮消除的是正文已经安全落盘后的额外等待。

显式上传一开始就保留源书的阅读入口。进度区的“阅读”按钮可与上传状态共存，书架中的本地原件也仍可打开。普通本地导入没有增加自动上传。刷新已有云端副本时的保护继续保留，不能在副本替换期间通过新入口打开它。

上传得到可信回执后，如果源书或目标书正在阅读或打开，保存上传回执并显示“阅读记录待迁移”，不下载副本来阻挡本地阅读，也不把迁移标成完成。用户回到书房后重试会复用回执，不重复传送原件。开始迁移前同时保留源书和目标书的迁移锁，避免读取源状态与提交目标记录之间又打开其中一本。原有精确原文匹配、未解决引用保留及来源副本保留规则不变。

打开阶段已经为了校验可见资源建立了正文窗口。本轮把该窗口放进 `ReaderOpeningPreparation`，传入 `ReaderSession` 并由 `TextReadingView` 首次呈现直接使用。session 会核对章 ID、段落序号和完整 Passage，不能使用另一份原文的准备结果。

后续窗口只复用同章、同段落 ID 且原句完全相同的 `SourceTextOffsets`。超长 Unicode 段落不再为每个相邻窗口重新建立全段检查点。窗口仍保留 canonical 段落 ID，source range 和 Unicode scalar offset 仍指向原段落，显示预算未扩大。没有改变源文件、索引和可见资源的完整校验，也没有改动译文生成或译文缓存契约。

## 回归与测量

新增回归先在旧行为上执行。`testNewDownloadPresentsSavedSourceBeforeHeldRecords` 将 `/records` 挂起，旧代码在约 603.8 ms 的观察窗口结束时仍无 reader、无书架项。`testUploadDefersMigrationWhileSourceReaderHasNewWork` 证明旧代码会迁移活跃源书并清掉回执。这两条均出现预期失败后才修改产品行为。

同批次还暴露了 Task 1 强制刷新夹具的问题。`testForcedRefreshWaitsForTheInFlightShelfAndItsQueuedRecheck` 对每个请求重复 fulfill 同一个 expectation。本轮改为只在第一个请求 fulfill，并独立断言总计恰好两次请求，分别对应进行中的刷新和强制重查，没有关闭 over-fulfill 检测。

| 检查 | 结果与范围 |
| --- | --- |
| Swift 语法与空白检查 | 11 个本领域 Swift 文件 `swiftc -parse` 通过，`git diff --check` 通过；这不等于类型检查或应用运行验收 |
| 首次下载挂起 records | 旧行为失败已观察；修复后通过，records 未释放前 reader 已发布，约 12.658 ms |
| 源书活跃延后迁移 | 旧行为失败已观察；修复后通过，保留回执、源书阅读入口和新笔记，未向目标书迁移 |
| 上传中打开本地原件 | 新增 gate 挂起实际上传传输，在传输返回前检查可读源书 ID，并调用真实 `model.open(source)`；统一回归通过 |
| 完整性与恢复 | 现有 `ReaderOpeningTests` 含篡改、过期回执、账号边界、延后失败与恢复快照；本轮增加准备窗口来源核对；统一回归通过 |
| Unicode 窗口 | 新增相邻窗口复用、变更原句和变更章节拒绝复用断言；统一回归通过 |

原生应用本轮统一执行 99 项、零失败：书架活动 24 项、书架展示 22 项、打开 2 项、分页 42 项、视口 4 项和选择 5 项。Core 打开与窗口执行 14 项、零失败。完整性、恢复和窗口来源核对均在这 14 项中。强刷夹具现于 `LibraryActivityTests.swift:58–70` 用锁保护计数，只在 `count == 1` 时 fulfill，最后断言 `requestCount == 2`。

同一 Mac Debug 夹具为 3,000,000 bytes 的合成 Unicode 长段。旧路径测得首窗 45.259 ms，后续四窗分别为 40.690 / 40.620 / 40.140 / 39.730 ms。修复后沿用同一夹具和窗口预算，并逐窗断言新增全段 offset 准备量为零。修复后首窗为 36.263 ms，后续四窗为 0.0804 / 0.0773 / 0.0526 / 0.0575 ms。这是一组固定合成夹具的阶段耗时，不是 p95 或真机结果。

以上只测 Core 窗口准备。`reader != nil` 也只代表 session 发布，二者都不冒充可读首帧、物理 iPhone 延迟或整本打开时延。首窗仍需一次完整长段偏移准备。整包原件哈希和冷索引解码仍与总量相关。

## 评分证据与未验收项

按既定功能 30 / 交互 25 / 性能 25 / 边界 20 的规则记分。当前先保存能计分的断言与测量，由独立审阅结合统一回归核定分数，不能用实现完成补出 95 分。

功能证据对应“正文落盘后无需 records”“上传中可读源书”和“源书新记录仍有归属”。交互证据检查传输与可读状态能共存，迁移延后不伪装完成。性能证据比较相同合成长段的重复准备时间，另记录 records 挂起前后 session 是否发布。边界证据核对原件和内容身份。段落 ID 与 Unicode offset 一并检查，恢复回执也有对应断言。

本轮尚未建立首次云端目标窗口先读，也未实现磁盘分段解码。设计中的未来架构不计作已交付。真实可读首帧的 p95 和 Release 冷开大书尚无本轮数据，峰值内存与主线程长任务也未测量。实际 VoiceOver 与大字号仍需验证，上传进度按钮的画面和物理 iPhone 操作亦未验收。模拟器单元回归不能自动补齐这些分数。

实现与统一本地测试已有记录。独立审阅和源码交付另列状态，服务发布、TestFlight 与手机安装也分别记账。本文件不宣称当前改动已发布或真机通过。
