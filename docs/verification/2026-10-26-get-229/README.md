# GET-229 — Fullscreen exit and truthful reader shortcuts

Baseline: `893d48fac617a83ed7b241a7f5f31996e8f56613` in the public `getyak/leafhour` repository. Scope: [GET-229](https://linear.app/getyak/issue/GET-229). The original attachment remains private and is not copied into this evidence directory.

## Finding and change

The reader requested the browser Fullscreen API on F, but its Escape branch never requested an exit. Its only fullscreen button was inside the concealed tools header. In Chromium 153 automation, a trusted Escape was delivered to the page while `fullscreenElement` stayed `HTML`; in WebKit 26.6, Escape exited natively without a page keydown. An owned, headed Chromium window with macOS system input also exited natively at baseline. The historical screenshot proves the missing visible exit; these results do not establish a failure of every physical browser Escape.

The existing reader keyboard owner now forwards an unclaimed Escape to the same controller that handles F and the explicit exit. That exit-only path cannot enter fullscreen, ignores duplicate pending requests and checks the real native property after settlement. A rejected exit that races a successful external exit uses the observed final state without a false failure notice. Native `fullscreenchange` and `fullscreenerror` reconcile labels and visibility. Composing, editable, modified and held keys remain with their owners; all added listeners are released on unmount.

A light 44px button remains visible in fullscreen without hover. Opening the reader tools replaces it with the existing header exit, avoiding overlap on narrow screens. Hiding a focused exit returns focus to the visible reading pill without scrolling. Modal dialogs retain their existing inert boundary; the background control is not exempted from it. The browser can still exit fullscreen while a dialog is open.

Four-language help describes F where supported, Escape exit, and the possibility of simultaneously closing an overlay. It does not promise a cancellable two-Escape browser sequence. This follows the [Fullscreen standard's UI rules](https://fullscreen.spec.whatwg.org/#ui): browser close requests take precedence over page close watchers. No keyboard lock, browser security override or second overlay coordinator was added.
